# Общие Go CI и конфигурации линтеров

[FIN-372](https://finassist.youtrack.cloud/issue/FIN-372) переносит общие проверки Go-репозиториев в отдельный источник: `fin-assist/go-ci`. Реализация находится в `common/`, переиспользуемые workflows — в `.github/workflows/shared-*.yml`. Профили `service` и `library` сохраняют разные правила сервисов и библиотек. Подключение выполняется поэтапно; наличие общего исходника само по себе не означает, что все потребители переведены и приёмка завершена.

В этой части работы участвуют 15 Go-репозиториев из таблицы ниже. Android, contracts и infra не подключаются к Go-профилям. Их специализированные проверки не заменяются Go CI.

## Источник и неизменяемая ссылка

По [FIN-516](https://finassist.youtrack.cloud/issue/FIN-516) потребители выбирают защищённую ветку `main` через `@main` в вызовах workflow и `@refs/heads/main` в вызовах Actions. Новый запуск после мержа в `go-ci` получает новый workflow. Точные байты общего кода в пределах запуска определяет `job.workflow_sha`. Профиль и локальные исключения задаются в `.finassist-ci.json` без поля `revision`.

Локальные команды разрешают SHA `refs/heads/main` из приватного `go-ci`, используя локальную авторизацию GitHub CLI (`gh auth login`). Для воспроизведения проверки укажите SHA из отчёта сборки, например `FINASSIST_CI_REVISION=<sha> make lint`. Bootstrap продолжает проверять SHA, origin и содержимое локального кэша. Полный повтор workflow разрешает ветку заново, повтор отдельных упавших jobs сохраняет SHA прошлого запуска.

При переходе FIN-516 первоначальный контракт FIN-372 остаётся совместимым: потребитель закрепляет **полный commit SHA**, обновления приходят отдельными PR через Renovate, откат возвращает прежний SHA. Версионные теги для общего CI не создаются и не перемещаются.

У потребителя `.finassist-ci.json` задаёт один источник локальных настроек:

```json
{
  "revision": "<полный SHA из 40 строчных шестнадцатеричных символов>",
  "profile": "service",
  "gosec_g115": false,
  "squawk_smallint": false
}
```

Значение `revision` должно быть настоящим доступным коммитом `fin-assist/go-ci`, содержащим общий код. Строка в примере — обозначение, bootstrap её отклонит. В `.github/workflows/ci.yml` все вызовы общего workflow закрепляются на том же SHA; параметр `revision` также совпадает с ним. Ссылка на ветку, сокращённый SHA или произвольный другой URL не заменяют этот pin.

Тонкий workflow потребителя оставляет у себя триггеры, минимальные permissions, явную передачу допустимого секрета и параметры профиля. Общие workflows выполняют Go/coverage, lint, совместимость публичного Go API библиотек, проверку SQL и сборку/проверку образа сервисов. У `assistant` отдельно включается образ fake-LLM, у `bank-bff` сохраняется HTTP smoke. Поведение образов задаётся разрешёнными параметрами, а не произвольной командой из вызывающего репозитория.

Потребитель, чьи Python-тесты запускают JavaScript, передаёт `setup_node: true` при вызове `shared-go.yml`. Параметр по умолчанию выключен и управляет установкой Node.js в Go job перед тестами скриптов.

`common/versions.json` закрепляет версии линтеров, `common/configs/` хранит эталоны. `common/render_lint.py` получает префикс goimports из `go.mod` и создаёт `.finassist-ci/generated/.golangci.yml` и `.finassist-ci/generated/.squawk.toml`. У golangci явно задан `relative-path-mode: gomod`: исключения сохраняют смысл после переноса файла в подкаталог. Сгенерированные конфиги и скачанный кэш не редактируют и не коммитят.

## Карта профилей и осознанных различий

Для каждой строки источник общий: `fin-assist/go-ci`. По FIN-516 workflow и локальные команды разрешают `main` в точный SHA, а локальная команда может явно использовать SHA из отчёта. Таблица фиксирует параметры, а не объявляет все репозитории уже переведёнными. Столбцы G115 и smallint означают включение соответствующего исключения, `false` оставляет правило активным.

Общий профиль библиотеки сохраняет FIN-322: запреты ядра процессного состояния, типизированный forbidigo, depguard и исключения тестов/`internal/pgtest`. Профиль сервиса позволяет сервису владеть процессом, сохраняя запреты обхода `finerr`, фреймворков, ORM и DI. Renderer проверяет точное имя репозитория из `GITHUB_REPOSITORY` в Actions или точный GitHub origin локально; название чужого fork не даёт исключения.

## Локальные команды и кэш

После подключения репозитория:

```sh
make lint-config
make lint
make lint-migrations BASE_REF=origin/main
```

`lint-config` получает закреплённый источник и генерирует конфиги; `lint` запускает закреплённый golangci с этим же конфигом. `lint-migrations` сравнивает `BASE_REF...HEAD`, запрещает изменение/удаление/переименование существующих `migrations/*.sql` и запускает Squawk на добавленных `*.up.sql`. Сначала нужно получить актуальную ссылку базовой ветки. В PR CI использует фактическую базовую ветку, а не всегда `main`. Для `bank-bff` проверка миграций не подключается.

Маленький `scripts/common_ci.py` копируется из `common/bootstrap.py`. Без команды он печатает путь общего `common/`; команда `render` генерирует конфиги. Bootstrap скачивает только фиксированный HTTPS-репозиторий, получает точный SHA с таймаутом и проверяет origin, HEAD и чистоту кэша. Git replace refs отключены: локальные `refs/replace` не могут подставить другое дерево под закреплённый SHA. Проверка не вызывает `git status` и clean filters: raw commit/tree сверяются с их Git object IDs, а каждый файл checkout — с blob hash из этого дерева. Подмена `core.worktree`, скрывающие изменения stat/index-настройки и локальные filter-команды не определяют принимаемый код; лишние файлы и симлинки отклоняются. Формат и raw-чтение объектов описаны в [Git user manual](https://git-scm.com/docs/user-manual#_object_storage_format) и [git-cat-file](https://git-scm.com/docs/git-cat-file). Изменённый кэш отклоняется; исправление — удалить каталог именно повреждённой версии и скачать её заново. Статус успешного скачивания не подменяется локальными правками.

Кэш версий расположен в `.finassist-ci/<SHA>/`. Потребители запускают общий каталог отрицательных bootstrap-кейсов против локальной копии транспорта. Совместимость старых вызовов с pin проверяется отдельно. Если меняется сам транспорт bootstrap, его копия обновляется явно вместе с pin: обычные изменения правил в `common/configs/` этого не требуют.

Обновление SHA создаёт отдельный каталог и сохраняет возможность вернуться к предыдущему коммиту. Уже скачанный чистый кэш позволяет bootstrap работать без сети при указании точного SHA. Полностью автономный запуск Go/npm-инструментов дополнительно требует их собственных заранее заполненных кэшей зависимостей.

При разработке самого общего исходника разрешён явный локальный путь:

```sh
python3 scripts/common_ci.py render --source ../go-ci/common
```

Это выбор рабочего дерева для разработки и проверки изменений, а не настройка production-потребителя. В Actions локальный `--source` разрешён только для обычных `push`/`pull_request` self-tests с непривилегированными правами; привилегированные события, например `pull_request_target` и `workflow_run`, отклоняются. Вызовы общего CI потребителей используют закреплённый источник. Исполнять изменяемое локальное дерево с write-токеном/секретами нельзя.

## Проверки и границы доверия

FIN-530: при новом коммите нативная группа отменяет прежние проверки того же PR.
В переиспользуемом Service CI у relay отдельная группа по workflow, номеру PR и
режиму (`service` или `qase90`). Остальные события получают уникальную группу
на попытку. Отмена дочернего прогона включается отдельно в [infra](https://github.com/fin-assist/infra/blob/main/docs/service-ci.md)
и проверяет актуальность исходного коммита перед отменой. Relay принимает оба
формата имени дочернего прогона, поэтому go-ci включается первым, а при откате
после включения обоих первым откатывается infra.

Переезд сохраняет имена обязательных checks через небольшие итоговые jobs потребителя: `go`, `lint`, `image`, `api`, `migrations` по применимому профилю. Такой job зависит от результата общего workflow и не должен стать успешным при ошибке, отмене или неожиданном пропуске зависимой проверки. Вложенные имена reusable jobs не заменяют старое required имя. На пилотах проверяются реальные опубликованные check contexts и их связь с итоговым SHA.

Снимок branch protection `main` от 28.10.2026, полученный чтением API без изменений настроек:

| Репозитории | Required contexts |
|---|---|
| `go-service-template`, `user`, `bank-statement-data`, `analytics`, `assistant` | `go`, `lint`, `image`, `migrations`, `Renovate policy tests`, `Renovate runtime contract` |
| Все девять библиотек, включая `go-library-template` | `go`, `lint`, `api`, `migrations`, `Renovate policy tests`, `Renovate runtime contract` |
| `bank-bff` | API branch protection вернул `Branch not protected` |

Для защищённых строк API вернул `strict: true`, checks от GitHub Actions (`app_id: 15368`). `bank-bff` нельзя считать защищённым по аналогии с остальными. В той же сверке API rulesets с учётом inherited rulesets вернул пустой список для всех 15 репозиториев; отдельная защита rulesets в этом снимке отсутствует. Настройка или изменение защит остаётся действием владельца и не выполняется этим переходом. Перед merge проверяется, что существующие требуемые контексты продолжают появляться; если потребуется настройка владельца, её явно выносят в план перехода.

FIN-515: unit, integration и API выполняются параллельно в трёх изолированных matrix jobs
с `fail-fast: false`, а tidy/vet/script/CHANGELOG checks — в отдельном job. Итоговый `check`
требует успеха всех jobs; прежний required `go` остаётся у потребителя. Coverage передаётся
между jobs только артефактами текущей попытки. При частичном повторе без всех трёх профилей
CI требует **Re-run all jobs**; детали и формат artifacts — в [shared-quality.md](shared-quality.md).

По решению владельца `fin-assist/bank-bff` использует последовательное выполнение
unit → integration → API в существующем `checks` job, после tidy/vet/script/CHANGELOG.
Matrix и отдельный aggregate job для него пропускаются; каждый total80, combined,
summary и artifact `coverage` сохраняются. Это исключение по точному repository identity,
без нового caller input или отката source SHA; остальные потребители сохраняют параллелизм.

Go unit/integration/API независимо сохраняют total80 всего production-знаменателя, PG18, race/count1, таймауты, inventory тестов, валидацию непустых выполненных suites и coverage artifacts. Combined не компенсирует провал уровня. У сервисов не появляется библиотечное исключение `internal/pgtest`; у библиотек исключается только точный пакет `<module>/internal/pgtest`, сами его тесты выполняются. N/A остаётся ограниченным фиксированной identity исходного `go-library-template`. Ни новый репозиторий с прежним module path, ни параметр профиля не наследуют это разрешение.

Компилятор тестов берётся из `go.mod`: `setup-go` сохраняет `GOTOOLCHAIN=local` для inventory и collectors. Закреплённые анализаторы coverage/gorelease и script fixtures запускаются отдельно с `GOTOOLCHAIN=auto`, поскольку их минимальная версия Go может быть выше версии проекта. Это не меняет компилятор production-кода и не снижает пороги.

Coverage guards и относящиеся к ним проверочные скрипты на данном этапе остаются в потребителях: это самостоятельные защиты, а не конфигурация линтера. Аналогично сохраняются FIN-264 и проверка совместимости публичного Go API, immutable SQL, up/down/up и специальные smoke/artifacts сервисов. Дубли удаляются только после фактической замены общим источником.

Обычный PR/fork CI имеет `contents: read`, checkout без сохранения credentials и не получает write-доступа. Передача `GO_MODULES_TOKEN` явная, без `secrets: inherit`; общий Go/API CI использует его только на доверенном `push`, а не при выполнении PR-кода. У образов остаётся передача токена через BuildKit netrc secret вместо build args или логов. Отсутствие доступа к приватному модулю не является основанием выдать секрет недоверенному PR или признать невыполненный gate успешным.

Claude, workflow контроллера Renovate и workflows выпуска библиотек остаются локальными намеренно. FIN-457 переносит
публикацию **сервисных** GitHub Release в [общий `shared-release.yml`](service-release.md):
отдельный job сохраняет `contents: write`, исполняет только закреплённый общий parser и
не исполняет PR-код. Локальные callers сохраняют свои triggers и inputs без передачи secrets.
FIN-456 выносит код Renovate в [общие actions](shared-renovate.md), сохраняя локальные
triggers, exact activation gate, main-only Environment и изоляцию credentials.
Триггеры, проверки происхождения PR, Environment и секреты разных автоматизаций не унифицируются.
Например, у `bank-bff` уже есть проверка источника PR до write-enabled Claude; унификация не должна её стереть.
Контроллер Renovate продолжает исполнять проверенный код `main` и не читает исполняемый PR-код/artifacts
с write-токеном. Владелец по-прежнему выпускает теги библиотек сам.

FIN-457 также описывает [общий runner тестов и coverage](shared-quality.md),
[упаковку stage-артефактов](stage-artifacts.md) и [parser CHANGELOG](changelog-tooling.md).

### Приватный Go CI до перехода (FIN-491/FIN-494)

Пилот в `assistant` разделяет подготовку зависимостей и выполнение проверок. Доверенный `private-ci-inputs.yml` берётся из default branch `main` для `pull_request_target` внутри того же репозитория с целью `main` или защищённой `release/X.Y.Z`. Он читает `go.mod`, `go.sum` и `.finassist-ci.json` как данные. Он сверяет pin с историей `go-ci/main` и скачивает только версии приватных Go-модулей, закреплённые контрольными суммами. Для чтения `go-ci` и зависимостей нужен существующий `GO_MODULES_TOKEN` с доступом на чтение к этим репозиториям. Подготовка не запускает код PR.

Обычный `pull_request` находит успешный запуск подготовки для точной пары head/base SHA с `actions: read`. Он проверяет восстановленный Git bundle и хеши трёх файлов в своём checkout. Если обновлённая база изменила один из них, нужно синхронизировать ветку PR. Go получает файлы в локальном кэше; сборка образа получает те же файлы через отдельный локальный build context и временное монтирование BuildKit. Кэш с этими файлами не публикуется в Actions cache. Секреты зависимостей не передаются в PR-проверки. Обязательные проверки остаются красными при ошибке подготовки.

Артефакт содержит исходники зависимостей. Доверенный workflow потребителя задаёт `allowed_module_repositories` после сверки прав читателей исходников и артефактов. Новый приватный репозиторий можно добавить в список после такой же сверки и включения обновлённого списка в `main`. Подготовка отклоняет зависимости вне списка до обращения к ним с токеном. Fork PR не запускает доверенную подготовку. Для каждого сервиса отдельно проверяется его Dockerfile.

Библиотечный профиль FIN-494 (`profile: library` в вызове подготовки) добавляет контрольные суммы из двух последних стабильных тегов. Подготовка читает их lockfiles по SHA коммитов. Для сборки полного графа `gorelease` она также читает `go.mod` и `go.sum` из архивов уже проверенных приватных модулей. Перед каждым новым обращением она сверяет репозиторий с тем же allowlist, а архив получает только при наличии контрольной суммы ZIP. PR-проверка сверяет теги с подготовленным артефактом, получает модули и метаданные через loopback Go proxy и использует read-only токен текущего репозитория для проверки его живых тегов. Запросы к приватным путям не переходят на публичный proxy. Раскатка начинается после прохождения всех проверок библиотечного пилота на GitHub.

В профиле `library` потребитель запускает закреплённый `gorelease` из `scripts/api_check.py` и записывает его полный вывод в `gorelease.txt`, включая `# summary`. В репозитории без релизов скрипт использует `-base=none` и также сохраняет отчёт. Раздел `## errors in …` означает, что инструмент не загрузил пакеты для сравнения. Если тег изменился после подготовки или вышел новый релиз, сначала запустите доверенную подготовку заново, затем повторите CI для той же пары head/base. Проверки live tags в `api_check.py` выполняются до и после `gorelease`, включая публикацию тега после checkout.

В `bank-bff` этот же артефакт содержит два Git bundle для Qase 90. Доверенный workflow фиксирует SHA `bank-statement-data` и `analytics`, проверяет их принадлежность истории `main` и добавляет зависимости из обоих lockfiles в общий локальный кэш. При смене соседней ревизии обновите её pin в доверенном workflow и в проверке Qase 90; перед расширением списка приватных зависимостей сверяйте права читателей артефакта.

До появления автоматической подготовки в `assistant/main` владелец может вызвать её вручную из проверенного коммита отдельной ветки `fin491-ci-bootstrap`, используя существующую точку `renovate-policy.yml` для регистрации dispatch. В ручном запуске допустим точный SHA рассмотренного source PR, закреплённый самой служебной веткой. Перед слиянием пилота этот SHA включается в историю `go-ci/main`. Проверки пилота принимают такой артефакт только от точного SHA этой ветки и только для своей пары head/base. После включения автоматической подготовки bootstrap pin и ветка убираются.

## Обновление правила и откат

Общее правило меняется в `common/` одного source PR. Его self-check workflow проверяет рабочее дерево: bootstrap/render, workflows и реальные разрешённые/запрещённые lint-случаи. После ревью и команды владельца source коммит становится доступным потребителям.

FIN-447 добавил контроллер Renovate самого source; FIN-456 переносит его код в [общие actions и регрессии](shared-renovate.md), сохраняя [локальные данные и отдельную активацию](renovate-policy.md). После явной активации он обрабатывает bot-only dependency PR по `shared-source` и двум policy checks; source-код по-прежнему проходит обычный merge владельца. Go-компилятор/toolchain, включая версии setup-go в reusable workflows и смешанные PR, остаётся ручным. Baseline и подписанные metadata проверяются общим рассмотренным контроллером; изменение не распространяет активацию, secrets или внешние защиты на потребителей и не меняет `common/bootstrap.py`.

Сверка 28.10.2026: `RENOVATE_POLICY_ENABLED=true` у 11 существующих Go-репозиториев; их рассмотренный `renovate-base.json` публикуется существующим контроллером в `base.json` ветки `renovate-policy` после merge. У `go-grpc`, `go-migrate`, `go-worker` флаг равен `false`, поэтому новые managers/group размещены непосредственно в действующем `renovate.json`, без зависимости от baseline-sync; прежние presets, метаданные FIN-211 и запрет native automerge сохранены. У `bank-bff` новый прямой `renovate.json` также не активирует контроллер. Наличие флага/ветки не подменяет проверку конкретного запуска после merge; активация выключенных контроллеров не входит в FIN-372.

### Переход и откат по FIN-516

1. Влить совместимый источник в защищённую ветку `go-ci/main` после ревью и обязательных проверок.
2. Во всех 15 потребителях включить на default branch совместимый workflow подготовки приватных зависимостей. Он распознаёт и старые PR с pin, и CI-попытки с branch ref. Это требуется до удаления `revision`, поскольку GitHub загружает доверенный workflow из default branch потребителя.
3. Переключить все потребительские workflow и локальные конфигурации, сохранив обязательные jobs. Обновить настройки Renovate в репозитории так, чтобы bot не предлагал закрепить общий branch ref. Для совместимости необходима актуальная копия локального транспорта. Проверять сервисные и библиотечные профили при общей миграции.

Новый доверенный producer запускается по событию `workflow_run: in_progress` для PR CI, сверяет репозиторий и workflow по API GitHub и находит SHA общего workflow точной попытки. При нескольких разных SHA или несовпадении source с историей `go-ci/main` подготовка блокируется. Она по-прежнему читает только Go-манифесты и конфигурацию PR как данные, а для исполнения берёт только код доверенного reusable workflow. Имя артефакта в FIN-516 зависит от PR head и разрешённого SHA, поэтому сдвиг base не ломает повторный запуск. Содержимое Go-манифестов всё равно сверяется с фактическим checkout PR. Проверки PR ждут успешный доверенный запуск с точным именем артефакта, получают указанный commit с Git bundle и проверяют его и контрольные суммы манифестов. Обновление `go-ci/main` между запуском CI и подготовкой не меняет источник уже начатой проверки.

Обычные изменения общего CI проходят PR, ревью и проверки в `go-ci`. Для отката общего изменения откройте revert там же. При откате самой миграции потребителя восстановите согласованный набор workflow, конфигурации, правил Renovate и версию локального bootstrap.

### Как проверить обновление на том же коммите потребителя

Сохраните SHA коммита потребителя и значение `Go CI source` из первого запуска.
После мержа проверенного PR в `go-ci/main` выполните **Re-run all jobs** для того же
CI. В новой попытке SHA коммита потребителя совпадает с исходным, а `Go CI source`
указывает на обновлённую ревизию общего CI. Для проверки можно также сравнить
`referenced_workflows[].sha` в метаданных двух попыток GitHub Actions. Сверьте
результаты обязательных проверок, применимых к обеим попыткам.

В PR-запуске для этой проверки оставьте PR открытым, поскольку доверенная подготовка
сверяет его текущее состояние. Для запуска на `main` выберите потребителя с подходящими
побочными эффектами: полный повтор CI сервиса может снова запустить публикацию его
production-образа. **Re-run failed jobs** сохраняет исходную ревизию общего workflow
и подходит для повторной проверки той же версии.

### Совместимость с прямым publisher

Этот интерфейс сохраняется для потребителей `shared-production-image.yml`. Пять сервисов с приватным relay используют описанный выше путь через общий publisher.

`shared-image.yml` собирает образ, выполняет smoke и извлекает stage-бинарь
из того же image ID. При подключении прямого publisher передайте
`prepare_production: ${{ github.event_name == 'push' && github.ref == 'refs/heads/main' }}` в `image-check`. На push в `main` CI сохраняет
архив основного образа и его контрольную сумму. Сборка использует права
чтения. Вынесенная публикация сохраняет отдельный результат CI для stage.

Добавьте в сервис `.github/workflows/production-image.yml` с явным ref защищённой ветки.

```yaml
name: Publish production image
on:
  workflow_run:
    workflows: [CI]
    branches: [main]
    types: [completed]
permissions:
  actions: read
  contents: read
jobs:
  publish:
    if: >-
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.event == 'push' &&
      github.event.workflow_run.head_branch == 'main' &&
      github.event.workflow_run.head_repository.full_name == github.repository
    permissions:
      actions: read
      contents: read
      packages: write
    uses: fin-assist/go-ci/.github/workflows/shared-production-image.yml@main
```

Publisher сверяет событие успешного push/main, идентичность репозитория
и путь исходного CI. Перед новой публикацией он проверяет статусы
`go`, `lint` и `image` конкретной попытки.
Затем он проверяет SHA, run ID, attempt и контрольные суммы скачанного
архива, сканирует его Trivy и формирует CycloneDX SBOM. Ошибка сканера
или уязвимость HIGH/CRITICAL блокируют публикацию. Для повтора повторите
job публикации, пока сохранён исходный архив. Исходный CI повторять для
этого не требуется. Если исходный CI завершился после частичного повтора,
используйте `Re-run all jobs` для исходного CI, чтобы собрать архив
успешной попытки. При повторе CI publisher сверяет существующий тег по SHA
с метаданными приватного пакета и датой мержа [go-ci #65](https://github.com/fin-assist/go-ci/pull/65).
Если образ опубликовали до этого мержа, workflow сохраняет его digest в сводке
и завершается без загрузки образа и формирования новой квитанции. Первые
публикации и повторы с тегом, созданным после перехода, идут по обычному пути.
Перед активацией проверьте приватность пакета и
доступ к нему GitHub Actions сервисного репозитория. GHCR создаёт первый
пакет с приватной видимостью. Workflow сверяет её до выдачи digest.

Для основного образа Docker получает время коммита потребителя как `SOURCE_DATE_EPOCH`.
Отдельный BuildKit с закреплённым digest нормализует метки конфигурации и файлов в новых слоях. При совпадающих
входах повторная сборка даёт одинаковый digest. Свидетельство публикации,
проверка Trivy и CycloneDX SBOM формируются в publisher.

Используется `sha-<полный SHA>`. Повтор с тем же digest идемпотентен,
существующий тег с другим digest блокирует публикацию. Версионный тег
`vX.Y.Z` относится к отдельному release-потоку с тегом владельца. Идентификатор опубликованного образа доступен в job summary. Для потребителя прямого publisher передайте этот digest в его существующую процедуру выкладки. Для возврата к рабочей версии используйте сохранённый digest предыдущей успешной выкладки того же потребителя.

Приватный artifact `production-evidence-…` содержит SBOM, отчёт Trivy и
provenance с digest GHCR, digest конфигурации из архива, Docker image ID,
source CI run/attempt и контрольными
суммами. Сохраняйте версии GHCR и доказательства, которые нужны для
деплоя и отката. GitHub Artifact Attestation для приватного репозитория
требует GitHub Enterprise Cloud и подключается после сверки тарифа.
Кластеру нужен отдельный запечатанный pull secret с токеном чтения пакетов.

## Порядок первоначального подключения и приёмка (FIN-372)

1. Подготовить общий source, self-checks, карту профилей и сверку защит. Source SHA должен существовать на GitHub до запуска consumer workflow, который на него ссылается.
2. Подключить два пилота: один обычный stateful сервис и одну библиотеку. Проверить полный CI, локальное совпадение конфигов, положительные/отрицательные lint-случаи, реальные имена required checks, обновление SHA и откат.
3. После пилотов подключить оба шаблона. В инструкциях создания нового репозитория менять только его module/import path и описание. **Не переписывать координаты** `fin-assist/go-ci`: координаты общего source должны остаться исходными. Фиксированную identity N/A в библиотечном guard также не переписывать.
4. Подключить остальные Go-репозитории, сохраняя параметры таблицы, HTTP smoke `bank-bff`, fake-LLM `assistant` и особенности release workflows. Удалять только заменённые дубли; README/AGENTS и локальные команды обновлять в том же PR.
5. Для каждого итогового SHA сопоставить прежние gates и новые результаты: CI, coverage suites, SQL/compatibility, artifacts, fork/secrets и lint probes. Проверить отсутствие открытых замечаний и оставшихся пунктов задачи.

Полная приёмка требует реальных успешных контрольных прогонов пилотов и всех подключённых репозиториев. Локальные self-tests общего кода, статическая карта или подготовленный consumer diff не подтверждают завершение всего перехода. Merge любого обычного PR, изменение branch protection, deployment, выпуск тегов и UI-прогоны требуют соответствующего отдельного разрешения владельца; FIN-372 их автоматически не разрешает.


## Перенос из сервисного шаблона

Решение владельца28.10.2026: общий источник размещается в отдельном `fin-assist/go-ci`. В `go-service-template` удаляются `common/` и source-only workflows/tests; оба шаблона остаются обычными потребителями. Меняются source URL, workflow repository, Renovate package identity и полный SHA вместе с matching bootstrap. Module paths сервисов/библиотек и фиксированная N/A identity не переименовываются. Откат этой первой миграции возвращает прежние координаты, pins и bootstrap одновременно.


FIN-456: общий Renovate не требует Go-профиля у Android/contracts/infra. Его production-код и
регрессии находятся в `common/renovate/`, конфигурация и runtime lock остаются у каждого потребителя.
Существующий Go bootstrap не меняется. [Подключение, единый pin и безопасный откат](shared-renovate.md).
