# Ручная выкатка сервиса

Откройте **Actions → Deploy production → Run workflow** в нужном сервисе и оставьте ветку `main`. После слияния изменений дождитесь зелёного CI и публикации образа. Если за это время изменился `main`, начните новый запуск. Сборка сама по себе не запускает выкатку.

Общий workflow проверяет исходный репозиторий, ручной запуск, SHA защищённого `main`, CI, приватную публикацию образа и isolated stage. Сначала он публикует в приватном пакете `production-<service>` команду версии `2.<ID запуска>.<попытка>`. Argo CD получает её через отдельное Application и сообщает активный образ и наличие кандидата. Если кандидат уже существует, **Deploy production** завершается с ошибкой до публикации новой версии приложения. Когда ручное продвижение включено и кандидата пока нет, выкатка разрешена.

Версия приложения имеет вид `1.<ID запуска>.<попытка>`. Перед миграциями кластер повторно проверяет состояние и записывает принятие команды. Успех **Deploy production** в GitHub означает, что кластер принял релиз. Состояние миграций, готовность реплик, паузу ручного продвижения и окончательное переключение трафика видно в Argo CD.

Перед сменой версии отдельная Job сохраняет в закрытом GitHub-репозитории инфраструктуры точный образ предыдущей активной ревизии. Если кластер не может подтвердить предыдущую версию или записать её, обычная выкатка останавливается до миграций. На первой установке без существующего сервиса история начинается с пустой записи. Для четырёх сервисов с БД он также содержит обычную Job с командой `migrate up` из того же образа по digest. Она применяет **все ожидающие SQL-миграции** и работает в более ранней волне синхронизации. Имя Job зависит от спецификации и ручного запуска релиза. После устранения причины сбоя новый запуск Action позволяет повторить миграции. Завершённая Job остаётся в кластере для повторной синхронизации. При ошибке остановитесь на версии, отмеченной dirty, и воспользуйтесь инструкцией сервиса по восстановлению миграций. У `bank-bff` этап миграций отсутствует.

## Workflow сервиса

Файл `.github/workflows/deploy.yml` вызывает общий workflow выкладки. Файл `.github/workflows/rollback.yml` с именем **Rollback production** аналогично вызывает `fin-assist/go-ci/.github/workflows/shared-production-rollback.yml@main` из job `rollback`. Publisher проверяет путь, событие `workflow_dispatch` и ссылку на защищённый `go-ci/main`. Каждый вызов явно передаёт `DEPLOY_DISPATCH_TOKEN` по имени. При откате общий workflow передаёт его дальше в задачу с Environment `production-request` сервиса.

```yaml
name: Deploy production
on:
  workflow_dispatch:
permissions: {}
jobs:
  deploy:
    uses: fin-assist/go-ci/.github/workflows/shared-production-deploy.yml@main
    secrets:
      DEPLOY_DISPATCH_TOKEN: ${{ secrets.DEPLOY_DISPATCH_TOKEN }}
```

## Разовое подключение

1. В `go-ci` создайте Environment `production-delivery`, ограниченный защищённой веткой `main`. Добавьте `DELIVERY_READ_TOKEN` с Contents/Actions Read для инфраструктуры, пяти сервисов и общего CI. Выделите отдельную учётную запись для публикации с записью только в пять приватных пакетов релизов, её логин в `REGISTRY_USER`, токен в `REGISTRY_TOKEN`. Для чтения истории задайте `RECEIPT_CREATOR_ID` (числовой ID выделенного автора записей). Предоставьте `DELIVERY_READ_TOKEN` право Deployments Read только на закрытый `infra`, а кластерной учётной записи — Deployments Write на этот репозиторий. В org GHCR заранее создайте пять **private** Helm-пакетов `production-<service>` под этой учётной записью. Для начальной публикации подходит пустой Helm chart версии `0.1.0`, диапазон Argo CD выбирает только `1.*`. Не предоставляйте сервисным GITHUB_TOKEN доступ к пакетам. В каждом сервисе создайте Environment `production-request` и разрешите в нём только ветку `main` (тип branch, точное имя без wildcard). Храните `DEPLOY_DISPATCH_TOKEN` только в этом Environment. У токена права Actions Write только на `go-ci`. Проверьте, что одноимённого секрета нет на уровне репозитория или организации и запуск с другой ветки отклоняется правилами Environment.
2. Для кластера используйте [bootstrap релизных приложений в infra](https://github.com/fin-assist/infra/blob/main/bootstrap/gitops/service-releases/README.md). Он регистрирует отдельный GHCR credential читателя, проверяет чтение опубликованных пакетов через Argo CD и передаёт сервисы пяти Application. Та же команда используется при восстановлении. Для команды и версии сервиса используйте отдельные Application с диапазонами `2.*` и `1.*` в одном и том же приватном OCI-пакете. Для первой публикации и штатных выкаток используйте ручной Action каждого сервиса. GitHub App продолжает читать приватный репозиторий инфраструктуры.

## Откат и хранение

Откройте **Actions → Rollback production → Run workflow** в репозитории сервиса и выберите `main`. По истории наблюдений кластером workflow находит предыдущий образ, который действительно обслуживал трафик. Если A сменилась на B и C ещё кандидат, откат снимает C и возвращает A. Если C уже стала активной, откат возвращает B. При сбое предыдущей выкатки до появления кандидата Action может восстановить текущий рабочий образ. При отсутствии готового Service используется последняя подтверждённая рабочая версия из истории. Откат сохраняет схему БД. Action завершается успешно после подтверждения активных endpoints целевого образа и снятия кандидата. Повтор одной команды сохраняет исходную цель отката.

Если очередная выкатка остановилась на миграции, запись кластера уже содержит образ, который обслуживал сервис до попытки. На чистой установке предыдущей версии ещё нет. При отсутствии подтверждённого образа Action сообщает об ошибке. После публикации проверьте завершение синхронизации и готовность активной ревизии сервиса в Argo CD. Следующая обычная выкатка вновь выбирает текущий защищённый `main`.

Сохраняйте в GHCR текущий и предыдущие рабочие образы и пакеты релизов. Для каждого сохранённого пакета сохраняйте указанный в нём digest образа. Не применяйте к этим пакетам общую очистку по возрасту или числу версий. Истечение срока хранения CI artifacts не удаляет эти версии из GHCR. Сохраните историю прочитанных пакетов, source SHA, pipeline runs и результатов выкладки в эксплуатационном журнале.
