# Ручная выкатка сервиса

Откройте **Actions → Deploy production → Run workflow** в нужном сервисе и оставьте ветку `main`. После слияния изменений дождитесь зелёного CI и публикации образа. Если за это время изменился `main`, начните новый запуск. Сборка сама по себе не запускает выкатку.

Общий workflow проверяет исходный репозиторий, ручной запуск и его попытку, SHA защищённого `main`, CI, приватный publisher и isolated stage. Он публикует закрытый Helm-пакет `production-<service>` версии `1.<ID ручного запуска>.<попытка>` и проверяет его чтением из GHCR. Успех в GitHub означает, что релиз доступен Argo CD. Статус синхронизации, завершение миграций, паузы canary и готовность рабочей версии смотрите в Application `production-<service>`. Продолжайте canary согласно эксплуатационной инструкции приложения, с проверкой трафика и анализа на каждой паузе.

Пакет содержит Rollout одного сервиса. Для четырёх сервисов с БД он также содержит обычную Job с командой `migrate up` из того же образа по digest. Она применяет **все ожидающие SQL-миграции** и работает в более ранней волне синхронизации. Имя Job вычисляет действующий генератор по её спецификации. Завершённая Job остаётся в кластере для повторной синхронизации. При ошибке остановитесь на версии, отмеченной dirty, и воспользуйтесь инструкцией сервиса по восстановлению миграций. У `bank-bff` только Rollout.

## Разовое подключение

1. В `go-ci` создайте Environment `production-delivery`, ограниченный защищённой веткой `main`. Добавьте `DELIVERY_READ_TOKEN` с Contents/Actions Read для инфраструктуры, пяти сервисов и общего CI. Выделите отдельную учётную запись для публикации с записью только в пять приватных пакетов релизов, её логин в `REGISTRY_USER`, токен в `REGISTRY_TOKEN`. В org GHCR заранее создайте пять **private** Helm-пакетов `production-<service>` под этой учётной записью. Для начальной публикации подходит пустой Helm chart версии `0.1.0`, диапазон Argo CD выбирает только `1.*`. Не предоставляйте сервисным GITHUB_TOKEN доступ к пакетам. В каждом сервисе создайте Environment `production-request` и разрешите в нём только ветку `main` (тип branch, точное имя без wildcard). Храните `DEPLOY_DISPATCH_TOKEN` только в этом Environment. У токена права Actions Write только на `go-ci`. Проверьте, что одноимённого секрета нет на уровне репозитория или организации и запуск с другой ветки отклоняется правилами Environment.
2. Сохраните действующую GitHub App для доступа Argo CD к Git. В Argo заведите отдельный project-scoped Helm repository Secret с `type=helm`, `enableOCI=true`, `url=ghcr.io/fin-assist`, `project=production-releases`, `username` и `password` учётной записи с Packages Read. Передайте credential существующим механизмом запечатанных секретов. У kubelet отдельный pull secret для образов. Убедитесь, что он читает каждый точный digest в manifest. Образ и пакет релиза требуют независимой проверки доступа.
3. Скрипт `common/scripts/production_argocd.py SERVICE project` выводит общий AppProject с правами только на Jobs и Rollouts в namespace приложений. Режим `application` выводит отдельный Application с отключённой автосинхронизацией, `exclusions` выдаёт Kustomize patches для прежнего runtime Application. Все три режима только печатают JSON.
4. Подключайте по одному сервису в согласованное окно. Зафиксируйте revision, манифесты и resource tracking действующего Application, текущий digest и успешные миграции. Дождитесь состояния Synced/Healthy и завершения прежней операции. Сохраните резервную копию спецификаций Application. Опубликуйте первый пакет ручным Action. Сначала создайте новый Application с выключенным auto-sync и сравните полученные через Argo манифесты с результатом генератора и работающим сервисом. Проверьте выбранную версию, digest, миграционную Job и canary.
5. При выключенном prune и отсутствии операций добавьте выданные exclusions **к уже имеющимся** `spec.source.kustomize.patches` прежнего Application. Они исключают из результата рендера только Rollout и миграционную Job этого сервиса. Сверьте новый render до sync. Перенесите tracking только соответствующих живых объектов на новый Application по используемому в кластере методу Argo CD. Сверьте их UID, `spec` и исходный tracking перед изменением метаданных. У прежнего Application должны остаться его Service, политики и маршруты. Проверка FailOnSharedResource в новом Application должна проходить. Не используйте prune, force, replace или удаление Application с каскадом. При несовпадении остановите переключение и восстановите сохранённые метаданные и exclusions.
6. Включите `spec.syncPolicy.automated.enabled=true` только у проверенного Application. Проследите первый sync, работу миграций, штатные canary-паузы и переход стабильной ревизии. Храните выбранные exclusions и Application вместе с инструкцией восстановления кластера. После повторного bootstrap сверяйте их перед sync прежнего runtime. Формат исходников и рендерер остаются в приватном репозитории инфраструктуры, новый релиз забирает их из защищённого main.

## Откат и хранение

В истории конкретного Application найдите предыдущую **успешную рабочую** версию пакета, сверьте сервис, digest и совместимость прежнего бинарника с текущей схемой БД. При откате в ходе canary сначала используйте штатный abort из инструкции сервиса. Для долговременного отката задайте в `spec.source.targetRevision` точную прежнюю версию вместо диапазона `1.*` и синхронизируйте этот Application. Убедитесь, что Job этого релиза уже успешно завершена, пройдите проверки здоровья. SQL down автоматически не выполняется. Сохраните точную версию до публикации исправленного `main`, затем сверьте новый пакет и верните `1.*`. Изменение Deployment напрямую оставляет расходящееся желаемое состояние.

Сохраняйте в GHCR текущий, предыдущие рабочие и находящиеся в canary образы и пакеты релизов. Для каждого сохранённого пакета сохраняйте указанный в нём digest образа. Не применяйте к этим пакетам общую очистку по возрасту или числу версий. Истечение срока хранения CI artifacts не удаляет эти версии из GHCR. Сохраните историю прочитанных пакетов, source SHA, pipeline runs и результатов выкладки в эксплуатационном журнале.
